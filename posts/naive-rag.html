RAG Isn't Dead. Naive RAG Is.

August 2026

Every few months, a wave of posts declares retrieval-augmented generation dead, usually right after a new model ships with a bigger context window. The argument is always some version of: "why bother chunking and embedding documents when you can just paste the whole thing into the prompt?"

For a narrow set of use cases, that's a fair point. For most of the systems I actually care about (support systems working off a growing knowledge base, agents that need current pricing or inventory, anything where the source data changes daily) it isn't, and the people making the argument are usually comparing a bigger context window against the worst possible version of RAG.

Because there is a version of RAG that deserves to die. It's the one that got built in a weekend: split every document into fixed 500-token chunks regardless of what's actually in them, embed with an out-of-the-box model, retrieve the top three by cosine similarity, staple them into a prompt, done. It technically works on the happy-path demo query and falls apart the moment a real question needs information that got split across two chunks, or phrased in words that don't overlap semantically with the source text.

That's not a RAG problem. That's a "we skipped every decision that RAG actually requires" problem. The systems that hold up in production usually get there by taking a few of these seriously instead of defaulting on all of them:

  • Chunking that respects structure. Splitting by section, heading, or logical unit instead of a fixed token count, so a chunk is a coherent idea instead of an arbitrary slice.
  • Hybrid retrieval. Combining semantic search with keyword/BM25 so you're not solely dependent on embedding similarity catching a query that's phrased differently than the source.
  • Re-ranking before generation. Pulling back more candidates than you need and using a cheaper, more precise step to pick the best few, instead of trusting the first-pass retrieval score.
  • Freshness as a first-class concern. If the underlying data changes daily, the retrieval index needs a real update pipeline, not a one-time embedding job someone ran at launch.

None of that is exotic. It's also not the version most teams ship, because the naive version answers enough queries correctly to feel done. It's only once real usage starts hitting the edges (the paraphrased question, the fact that moved to a different page, the answer that needed two documents synthesized together) that the gap between "retrieval that works on the demo" and "retrieval you can trust" becomes visible.

Bigger context windows are a genuine tool, and for some workloads they're the right one. But "the context window got bigger" and "you no longer need a real retrieval strategy" are different claims, and conflating them is how you end up rebuilding the same broken system twice: once with embeddings, once by just paying more tokens for the privilege of the same missed answer.
